How it is kept

The token and the chat id are written to admin.json, next to the app, with the permissions of a secret (0600). The file is in .gitignore, so it cannot be committed by accident. The token is never sent back to the page — only the first and last four characters are.

The question asked before a browser opens

are you a person?

Opening a browser on this machine costs a screen, a profile and a Chromium — and anybody who knows the address can ask for one. So the door has a question at it.

Turning it off keeps the keys: it is the way out when a widget misbehaves and the door has to be opened again.

The page asks the server for the site’s key when it loads — it is public, and no secret is in it — and Cloudflare gives back a token. The token is a claim, not a proof, so the server asks Cloudflare about it before anything is opened. The secret never leaves this machine and is never sent back to the page.

Saving takes effect at once. The next page load on the server’s own pages uses the keys as they are now — and so does the copy of the pages that lives somewhere else, because that copy asks this server for the question too. There is nothing to download again and nothing to upload again.

An answer that is not good stops it. If Cloudflare cannot be reached, or the token is not good, no browser is opened: a check that can be walked around is not a check. The visitor is left looking at the capture, and the panel says why.

Both keys can also come from the environment: ICLOUD_TURNSTILE_SITE_KEY and ICLOUD_TURNSTILE_SECRET. Either one being there means the question is asked — a page with the key and a server with no secret is a misreading, and it stops the door rather than opening it.

What is set in this panel is what is used; the environment is what the machine falls back to until then. The panel says which one is in use.

The question asked before a browser opens

Google’s answer — are you a person?

The same door, a different answer. Google’s reCAPTCHA is asked instead of Cloudflare’s when it has the keys — and it is the one that answers on a bare address of its own, which Cloudflare’s widget does not.

The two are fetched two different ways, and the invisible one refuses to answer unless the script was asked for with the key in it. Pick the one the key in Google’s console is.

The page asks the server for the site’s key when it loads — it is public, and no secret is in it — and Google gives back a token and a score. The token is a claim, not a proof, so the server asks Google about it before anything is opened. The secret never leaves this machine and is never sent back to the page.

The score is the verdict. The invisible kind says how likely it is that the person is a person. Below the score in this panel they are turned away, and the panel says why.

Either kind of key is read the same way. Google’s Enterprise keys say more than the plain ones do, and they say it in a second place: the name of the question, the host the answer was given on and the score are all in the answer, whether they are at the top of it or beside it.

Both keys can also come from the environment: ICLOUD_RECAPTCHA_SITE_KEY and ICLOUD_RECAPTCHA_SECRET. Either one being there means the question is asked — a page with the key and a server with no secret is a misreading, and it stops the door rather than opening it.

When both are set, Google’s is asked. Cloudflare’s widget refuses a bare address of its own accord, so on an address of its own there is only one question that can be answered.

What is set in this panel is what is used; the environment is what the machine falls back to until then. The panel says which one is in use.

The address the browsers leave from

live — the next browser that opens uses it

Fill the rest in, test it, and then turn this on. The browsers that open after this are turned on will leave from the proxy; the ones that are open now keep the address they were opened with.

Chromium cannot use a SOCKS5 proxy with a password — the browser says so before it opens. So: use HTTP, or whitelist this machine’s address in Decodo and use SOCKS5 with no password. HTTP loses nothing: the proxy is given the names and resolves them, so nothing is looked up here and nothing is said here about who is going where.

Then there is no user name and no password: the country is chosen by the address (country-us.gate.decodo.com) and the session is held by the port. This is the only way to keep SOCKS5, and it means this machine needs an address that does not change.

How it works

Every browser that opens leaves from the address of the group it is in, and a few visitors share an address — a household has two Apple IDs, not forty. The country is the visitor's own, so the browser and the address agree with each other.

The change is live for the browsers that open after it. The ones that are open keep the address they were opened with: a browser cannot be moved to another address while it is running.

The user name and the password are written to admin.json, with the permissions of a secret (0600), and the file is in .gitignore. The password is never sent back to the page — only whether there is one — so an empty field means keep the one that is there.

A copy of the pages that lives anywhere

the server stays where it is

The pages a visitor sees, and the engine that makes them live, as a zip. Unpack it into the folder your host serves — a cPanel, a bucket, anything — and the pages there will talk to this server, which keeps the browsers, the sessions and the sign-in.

The copy has to be told it may ask this server for things. A browser will not let a page on one host ask a server on another unless the server says it may — and it will say it may for this address and for that address only. So this is the address of the copy: the folder it was unpacked into, as the browser sees it, with https and no path.

The host has to serve the captures as files of their own. A host that answers every path with the same file — the single-page fallback that most Worker templates for one-page sites use — sends the visitor round in circles for ever: the launcher asks for the capture, the host answers with the launcher, and the page reloads without end. On a Worker, turn that fallback off; the zip holds a Worker and its settings, ready to be deployed as they are.

How to use it

1. Unpack the zip into the folder your host serves — often public_html, or a folder inside it.

2. Put that address in the box above — the copy's address, as the browser sees it — and save. The server has to know it may be asked by pages on that host, or the browser will not let them.

3. Open client.html through the address of that folder. That is all: there is nothing to run there, only pages.

4. The pages have to be able to reach this server, and the server has to be on https — a page on https talking to a server on http is refused by the browser.

The zip holds client.html, the captures in src/, the engine beside them, and a note. The captures are the same pages, with the same engine in them: what the visitor sees is what they would have seen here.

The zip carries no keys. The copy asks this server for the question it is to be asked, when the page loads, so the keys in the Turnstile tab are live in the copy too — there is nothing to unpack again and nothing to upload again.
